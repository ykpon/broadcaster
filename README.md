# Эфир

Веб-приложение для трансляции экрана, окна приложения или вкладки через **LiveKit SFU**. Go API и React/TypeScript интерфейс. Без регистрации: один ведущий и до 10 зрителей в комнате. Медиа всегда проходит через сервер.

## Запуск

Нужен Docker с Compose (на Windows/macOS — запущенный Docker Desktop в режиме Linux containers).

```sh
docker compose up --build -d
```

Откройте **http://localhost:8080**, создайте комнату, выберите источник и отправьте зрителям ссылку из панели «Позовите своих». Первый запуск скачивает образы и собирает клиент и сервер. Готовность: `docker compose ps`; журналы: `docker compose logs -f`. Остановить: `docker compose down`.

Локальная конфигурация предназначена для браузеров на том же компьютере. Ссылка localhost не работает на чужом компьютере. Для доступа из интернета настройте домен и публичный IP по инструкции ниже.

## Возможности

- Отдельные ссылки ведущего (с секретом во fragment `#key=`) и зрителя.
- Экран, окно или вкладка выбираются в системном диалоге браузера.
- Разрешения: исходное (до 4K), 720p, 1080p, 1440p, 2160p. Можно запросить от 15 до 120 FPS, в том числе во время эфира; фактические захват и кодирование могут работать с меньшей частотой.
- Перед эфиром выбирается VP8, VP9 или AV1. Доступность зависит от браузера, ОС и оборудования: при несовместимости приложение использует совместимый fallback, а фактически согласованный кодек виден в диагностике.
- Потолок видеобитрейта настраивается от 1 до 80 Мбит/с, аудио — от 32 до 320 кбит/с. Это верхние пределы для кодировщика, а не гарантированная пропускная способность или постоянный фактический битрейт.
- Студия показывает параметры захвата и исходящую WebRTC-диагностику; зритель — кодек, битрейт, разрешение/FPS, пакеты, потери, пропущенные кадры, jitter и фактическую задержку буфера. Для неподвижного экрана фактический FPS может быть меньше выбранного.
- Маршрутизация звука зависит от выбранной поверхности: вкладка передаёт только свой звук, окно запрашивает звук выбранного окна, а весь экран — общий системный звук, включая Discord. В браузере без поддержки изоляции окна используется прежний fallback на весь системный звук. Отдельный регулятор громкости и mute есть у каждого зрителя; ведущий может мгновенно выключить публикуемую аудиодорожку. Превью ведущего всегда muted.
- Буфер воспроизведения зрителя выбирается как «Авто» или от 0.1 до 4.0 секунды и сохраняется как настройка конкретного браузера. Это предпочтение для браузера, а не гарантия точной задержки; неподдерживающий API браузер продолжает воспроизведение с автоматическим буфером.
- Полноэкранный просмотр, вписывание/заполнение, ожидание эфира и повторный запуск трансляции в той же комнате без смены зрительской ссылки.

WebRTC передаёт сжатый поток с потерями: приложение не гарантирует пиксельно идентичные исходнику кадры 1:1, даже при высоком потолке битрейта.

Основной сценарий ведущего: актуальный Chrome/Edge на компьютере. Зритель может использовать мобильный браузер. Захват системного звука зависит от ОС и типа поверхности; если звук не предложен или не выбран в системном диалоге, приложение не может добавить его самостоятельно. Микрофон не захватывается.

Игры можно транслировать через окно или монитор, если браузер захватывает их изображение. При чёрном кадре переключите игру в оконный режим без рамки или выберите весь монитор. Захват exclusive fullscreen и защищённого видео не гарантируется. Это браузерный screen capture, специального драйвера захвата игр нет.

## Развёртывание в интернете

1. Направьте DNS A-запись своего домена на IPv4 сервера.
2. Скопируйте `.env.example` в `.env` и заполните `APP_URL`, `LIVEKIT_URL`, `LIVEKIT_NODE_IP`, случайный API key и секрет длиной минимум 32 символа. Секрет передаётся только контейнерам Go и LiveKit. Для домена `stream.example.com` значения URL должны быть `https://stream.example.com` и `wss://stream.example.com/livekit`.
3. Возьмите [пример Nginx-конфигурации](deploy/nginx.conf.example), замените домен и пути сертификата. Директива `map` должна находиться внутри общего блока `http {}`, а `upstream` и `server` — рядом с другими виртуальными хостами. Если сертификаты и HTTP→HTTPS redirect уже настроены, добавьте в существующий HTTPS `server` только два upstream и два location из примера.
4. Проверьте и примените Nginx: `sudo nginx -t && sudo systemctl reload nginx`.
5. Откройте/пробросьте **80/TCP, 443/TCP, 7881/TCP, 50000–50050/UDP** на Docker-хост. Порты 8080 и 7880 Compose публикует только на `127.0.0.1`, поэтому они не должны быть открыты в firewall. Укажите публичный IP хоста, а не адрес контейнера, в `LIVEKIT_NODE_IP`. WebSocket идёт через Nginx, медиа — непосредственно в LiveKit по опубликованным портам.
6. Выполните `docker compose up --build -d --remove-orphans`. Флаг удалит контейнер `proxy` от прежней версии Compose; именованные тома Caddy он не удаляет. HTTP вне localhost не подходит для захвата экрана.

При работе в LAN используйте доступное всем клиентам имя с доверенным HTTPS и IP Docker-хоста. Если внешний домен применяется внутри той же LAN, маршрутизатору может требоваться NAT loopback.

По умолчанию есть UDP и ICE/TCP fallback. TURN/TLS не включён: в корпоративных сетях, разрешающих только HTTPS на 443, соединение может не установиться. Для таких сетей нужен отдельный TURN/TLS endpoint и соответствующая конфигурация LiveKit. Обычный HTTP reverse proxy не заменяет TURN.

При потолке 80 Мбит/с и 10 зрителях upload ведущего к SFU составляет около 80 Мбит/с, а исходящий трафик SFU может приближаться к 800 Мбит/с плюс накладные расходы протоколов. Это расчёт по установленному потолку, а не результат нагрузочного теста: фактический трафик меняется вместе с содержимым, кодеком, состоянием сети и решениями браузерного кодировщика. Сервер пересылает поток и не выполняет перекодирование; отдельные разрешения для каждого зрителя в эту версию не входят.

## Жизненный цикл и доступ

Go хранит комнаты в памяти; один экземпляр API на отдельный экземпляр LiveKit. После рестарта комнаты завершаются. При запуске API удаляет старые комнаты с префиксом `broadcast-` в этом LiveKit. Не запускайте несколько копий API против одного LiveKit.

Пустая комната без ведущего и зрителей живёт один час; любое подключение сбрасывает этот срок. Остановка трансляции или остановка захвата в системном интерфейсе браузера убирает медиапоток, но сохраняет комнату и подключения зрителей: после нового запуска изображение и звук появляются у них автоматически. Отдельная кнопка «Закрыть комнату» завершает её сразу; страница ещё 10 минут сообщает о завершении. API сверяет состояние с LiveKit каждые 3 секунды, без зависимости от webhook.

Права зрителя запрещают публикацию аудио, видео и data packets. Ведущему разрешены только screen-share источники; фиксированная identity гарантирует одного ведущего (новая сессия студии отключает старую). Токен подключения действует 60 секунд; LiveKit поддерживает уже установленную сессию. Комнаты не создаются автоматически по старому токену: `auto_create: false`. Выданное зрителю место резервируется на 90 секунд и продлевается, пока участник присутствует. Это ограничивает гонки при одновременном входе; после ухода место освобождается не мгновенно.

Ссылка ведущего даёт право управления: не пересылайте её зрителям. Публичный список комнат отсутствует, но любой обладатель ссылки просмотра может войти. Это доступ по ссылке, не end-to-end encryption: сервер имеет доступ к медиапотоку. HTTP/API защищены same-origin проверкой и простым IP rate limit; публичный сервис большого масштаба потребует отдельной защиты от злоупотреблений.

## Разработка и проверки

```sh
go test ./...
go vet ./...
cd web
corepack enable
pnpm install --frozen-lockfile
pnpm test
pnpm run build
pnpm test:e2e
```

Go 1.26+, Node 24+, pnpm 11.19.0. Production Docker build выполняет Go tests/vet, тесты качества и TypeScript build. Сквозные тесты запускаются отдельно при работающем `docker compose up`: на Windows используется установленный Edge, на других ОС установите Chromium командой `pnpm exec playwright install chromium`. Для frontend development `pnpm dev` проксирует `/api` на Go `localhost:8080`; при отдельном запуске Go задайте `APP_URL` под origin dev-сервера и доступные LiveKit URLs.

Проверено 21.09.2026: 60 frontend unit-тестов, production TypeScript/Vite build, Go tests/vet. Сквозной сценарий покрывает публикацию видео и аудио через настоящий SFU, остановку и повторный запуск в той же комнате с автоматическим возобновлением у зрителя, параметры маршрутизации звука вкладки/окна/экрана, регулировку громкости/mute, смену настроек качества, зрительский буфер и диагностику приёма, десять отдельных зрительских сессий, отказ одиннадцатому, завершение комнаты, мобильную вёрстку 390 px и ошибку отсутствующей комнаты; для запуска требуется работающий Docker Compose. Только источник захвата в автоматическом тесте заменён canvas-видео и генерируемым аудио. Реальные VP9/AV1, стабильные 4K120, игры и точная задержка буфера зависят от браузера, ОС, оборудования и сети и не заявляются как аппаратно подтверждённые.

Структура: `cmd/server` — запуск, `internal/broadcast` — API и LiveKit RoomService, `web/src` — клиент, `deploy` — LiveKit и пример конфигурации Nginx. REST API: создание `POST /api/rooms`, состояние `GET /api/rooms/{id}`, токены `POST .../host-token` и `.../viewer-token`, завершение `POST .../end`. Host-запросы принимают `{ "hostSecret": "..." }`; viewer-запросы `{ "session": "..." }`, с пустой строкой при первом входе.

Ссылки на протоколы: [LiveKit deployment](https://docs.livekit.io/transport/self-hosting/deployment/), [Screen Capture API](https://www.w3.org/TR/screen-capture/).

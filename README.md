# Эфир

Веб-приложение для трансляции экрана, окна приложения или вкладки. Go API и React/TypeScript интерфейс. Без регистрации: один ведущий выбирает перед каждым запуском **P2P — напрямую** либо **Через сервер** (LiveKit SFU) и задаёт лимит зрителей. По умолчанию выбран серверный режим и лимит 10; настроенного верхнего предела нет.

## Запуск

Нужен Docker с Compose (на Windows/macOS — запущенный Docker Desktop в режиме Linux containers).

```sh
docker compose up --build -d
```

Откройте **http://localhost:8080**, создайте комнату, выберите способ подключения и лимит зрителей, затем источник и отправьте зрителям ссылку из панели «Позовите своих». После остановки эфира режим и лимит можно изменить перед повторным запуском; открытые страницы зрителей подключатся к новому эфиру автоматически. Первый запуск скачивает образы и собирает клиент и сервер. Готовность: `docker compose ps`; журналы: `docker compose logs -f`. Остановить: `docker compose down`.

Локальная конфигурация предназначена для браузеров на том же компьютере. Ссылка localhost не работает на чужом компьютере. Для доступа из интернета настройте домен и публичный IP по инструкции ниже.

## Возможности

- Отдельные ссылки ведущего (с секретом во fragment `#key=`) и зрителя.
- Выбор между прямым P2P и раздачей через LiveKit перед каждым запуском. Лимит зрителей — любое положительное целое десятичное число без продуктового максимума; реальная вместимость зависит от ресурсов и сети.
- Экран, окно или вкладка выбираются в системном диалоге браузера.
- Разрешения: исходное (до 4K), 720p, 1080p, 1440p, 2160p. Можно запросить от 15 до 120 FPS, в том числе во время эфира; фактические захват и кодирование могут работать с меньшей частотой.
- Перед эфиром выбирается VP8, VP9 или AV1. Доступность зависит от браузера, ОС и оборудования: при несовместимости приложение использует совместимый fallback, а фактически согласованный кодек виден в диагностике.
- Потолок видеобитрейта настраивается от 1 до 80 Мбит/с, аудио — от 32 до 320 кбит/с. Это верхние пределы для кодировщика, а не гарантированная пропускная способность или постоянный фактический битрейт.
- Студия показывает параметры захвата и исходящую WebRTC-диагностику для выбранного транспорта, включая число успешных и неуспешных P2P peers; зритель — кодек, битрейт, разрешение/FPS, пакеты, потери, пропущенные кадры, jitter и фактическую задержку буфера. Для неподвижного экрана фактический FPS может быть меньше выбранного.
- Маршрутизация звука зависит от выбранной поверхности: вкладка передаёт только свой звук, окно запрашивает звук выбранного окна, а весь экран — общий системный звук, включая Discord. В браузере без поддержки изоляции окна используется прежний fallback на весь системный звук. Отдельный регулятор громкости и mute есть у каждого зрителя; ведущий может мгновенно выключить публикуемую аудиодорожку. Превью ведущего всегда muted.
- Буфер воспроизведения зрителя выбирается как «Авто» или от 0.1 до 4.0 секунды и сохраняется как настройка конкретного браузера. Это предпочтение для браузера, а не гарантия точной задержки; неподдерживающий API браузер продолжает воспроизведение с автоматическим буфером.
- Полноэкранный просмотр, вписывание/заполнение, ожидание эфира и повторный запуск трансляции в той же комнате без смены зрительской ссылки.

WebRTC передаёт сжатый поток с потерями: приложение не гарантирует пиксельно идентичные исходнику кадры 1:1, даже при высоком потолке битрейта.

В P2P каждый зритель получает отдельное прямое WebRTC-соединение: исходящий трафик и нагрузка ведущего растут примерно пропорционально числу зрителей. Участники могут увидеть сетевые адреса друг друга через ICE. Go-сервер обрабатывает управление, сигналинг и STUN, но не пересылает P2P-медиа. Встроенный STUN не является TURN и не гарантирует прохождение NAT/firewall; если прямое соединение не устанавливается, появляется ошибка. Автоматического перехода на LiveKit нет: ведущий может сам остановить эфир и выбрать «Через сервер».

В серверном режиме ведущий отправляет один поток в LiveKit, а SFU пересылает его зрителям. Порты LiveKit для медиа нужны только этому режиму.

Основной сценарий ведущего: актуальный Chrome/Edge на компьютере. Зритель может использовать мобильный браузер. Захват системного звука зависит от ОС и типа поверхности; если звук не предложен или не выбран в системном диалоге, приложение не может добавить его самостоятельно. Микрофон не захватывается.

Игры можно транслировать через окно или монитор, если браузер захватывает их изображение. При чёрном кадре переключите игру в оконный режим без рамки или выберите весь монитор. Захват exclusive fullscreen и защищённого видео не гарантируется. Это браузерный screen capture, специального драйвера захвата игр нет.

## Развёртывание в интернете

1. Направьте DNS A-запись своего домена на IPv4 сервера.
2. Скопируйте `.env.example` в `.env` и заполните `APP_URL`, `STUN_URL`, `LIVEKIT_URL`, `LIVEKIT_NODE_IP`, случайный API key и секрет длиной минимум 32 символа. Секрет передаётся только контейнерам Go и LiveKit. Для домена `stream.example.com` значения URL должны быть `https://stream.example.com`, `stun:stream.example.com:3478` и `wss://stream.example.com/livekit`. `STUN_PORT` задаёт опубликованный UDP-порт (по умолчанию 3478); публичный номер в `STUN_URL` должен совпадать с доступным извне портом.
3. Возьмите [пример Nginx-конфигурации](deploy/nginx.conf.example), замените домен и пути сертификата. Директива `map` должна находиться внутри общего блока `http {}`, а `upstream` и `server` — рядом с другими виртуальными хостами. Если сертификаты и HTTP→HTTPS redirect уже настроены, добавьте в существующий HTTPS `server` только два upstream и два location из примера.
4. Проверьте и примените Nginx: `sudo nginx -t && sudo systemctl reload nginx`.
5. Откройте/пробросьте **80/TCP, 443/TCP и 3478/UDP** на Docker-хост. STUN UDP идёт напрямую к контейнеру приложения: Nginx его не проксирует. Для режима «Через сервер» дополнительно откройте **7881/TCP и 50000–50050/UDP** для LiveKit. Порты 8080 и 7880 Compose публикует только на `127.0.0.1`, поэтому их не нужно открывать в firewall. Укажите публичный IP хоста, а не адрес контейнера, в `LIVEKIT_NODE_IP`; WebSocket проходит через Nginx, медиа серверного режима — непосредственно в LiveKit.
6. Выполните `docker compose up --build -d app livekit` после проверки занятых портов и состава проекта через `docker compose ps --all`. HTTP вне localhost не подходит для захвата экрана.

При работе в LAN используйте доступное всем клиентам имя с доверенным HTTPS и IP Docker-хоста. Если внешний домен применяется внутри той же LAN, маршрутизатору может требоваться NAT loopback.

В серверном режиме LiveKit поддерживает UDP и ICE/TCP fallback. TURN/TLS не включён: в корпоративных сетях, разрешающих только HTTPS на 443, соединение может не установиться. В P2P-режиме доступны только прямые кандидаты через встроенный STUN; TURN и автоматический переход на LiveKit отсутствуют. Обычный HTTP reverse proxy не заменяет TURN.

При потолке 80 Мбит/с и 10 зрителях upload ведущего к SFU в серверном режиме составляет около 80 Мбит/с, а исходящий трафик SFU может приближаться к 800 Мбит/с плюс накладные расходы протоколов. В P2P-режиме upload ведущего при том же потолке может приближаться к 800 Мбит/с плюс накладные расходы, поскольку поток отправляется каждому зрителю отдельно. Это расчёты по установленному потолку, а не результат нагрузочного теста: фактический трафик меняется вместе с содержимым, кодеком, состоянием сети и решениями браузерного кодировщика. SFU пересылает поток без перекодирования; отдельные разрешения для каждого зрителя в эту версию не входят.

## Жизненный цикл и доступ

Go хранит комнаты в памяти; один экземпляр API на отдельный экземпляр LiveKit. После рестарта комнаты завершаются. Создание комнаты и P2P-эфир не требуют доступного LiveKit. Комната LiveKit создаётся только для запуска в серверном режиме и удаляется при остановке. При запуске API пытается удалить старые комнаты с префиксом `broadcast-` в этом LiveKit. Не запускайте несколько копий API против одного LiveKit.

Пустая комната без ведущего и зрителей живёт один час; любое подключение сбрасывает этот срок. Остановка трансляции или остановка захвата в системном интерфейсе браузера убирает медиапоток, но сохраняет комнату и логическое подключение зрителей: после нового запуска изображение и звук появляются у них автоматически, даже при смене транспорта. Отдельная кнопка «Закрыть комнату» завершает её сразу; страница ещё 10 минут сообщает о завершении.

В серверном режиме права зрителя запрещают публикацию аудио, видео и data packets. Ведущему разрешены только screen-share источники; фиксированная identity гарантирует одного ведущего. Краткоживущие LiveKit-токены относятся к конкретному запуску; старые токены не создают комнату автоматически (`auto_create: false`). В обоих режимах зрительское место резервируется на 90 секунд при неожиданном обрыве, а при штатном выходе освобождается сразу. Это ограничивает гонки при одновременном входе.

Ссылка ведущего даёт право управления: не пересылайте её зрителям. Публичный список комнат отсутствует, но любой обладатель ссылки просмотра может войти. Это доступ по ссылке, без проверки личности участников. В серверном режиме SFU имеет доступ к медиапотоку; в P2P-режиме WebRTC шифрует прямую передачу через DTLS-SRTP, а участники могут увидеть ICE-адреса друг друга. HTTP/API защищены same-origin проверкой и IP rate limit; публичный сервис большого масштаба потребует отдельной защиты от злоупотреблений.

## Разработка и проверки

```sh
go test ./...
go vet ./...
cd web
corepack enable
pnpm install --frozen-lockfile
pnpm test
pnpm run build
pnpm test:e2e
```

Go 1.26+, Node 24+, pnpm 11.19.0. Production Docker build выполняет Go tests/vet, тесты качества и TypeScript build. Сквозные тесты запускаются отдельно при работающем `docker compose up`: на Windows используется установленный Edge, на других ОС установите Chromium командой `pnpm exec playwright install chromium`. Для frontend development `pnpm dev` проксирует `/api` на Go `localhost:8080`; при отдельном запуске Go задайте `APP_URL` под origin dev-сервера и доступные LiveKit URLs.

Проверено 24.09.2026: 134 frontend unit-теста, production TypeScript/Vite build, Go tests/vet. Сквозной набор при работающем Docker Compose включает публикацию видео и аудио через настоящий SFU, остановку и повторный запуск в той же комнате, параметры маршрутизации звука вкладки/окна/экрана, регулировку громкости/mute, качество, зрительский буфер и диагностику, десять отдельных зрительских сессий и отказ одиннадцатому. Отдельный браузерный сценарий охватывает прямой P2P с двумя зрителями, выбранные ICE-пары без relay, лимит и отказ лишнему зрителю, автоматическую смену P2P → сервер без перезагрузки зрительских страниц и строгую ошибку при принудительном relay-only ICE без обращения к LiveKit. Есть проверки мобильной вёрстки 390 px и ошибки отсутствующей комнаты. Только источник захвата заменён canvas-видео и генерируемым аудио; API, сигналинг, STUN, WebRTC и LiveKit остаются реальными. Реальные VP9/AV1, стабильные 4K120, игры, точная задержка буфера и прохождение публичного NAT между двумя сетями зависят от браузера, ОС, оборудования и сети и не заявляются как подтверждённые этим локальным тестом.

Структура: `cmd/server` — HTTP и встроенный STUN, `internal/broadcast` — API, сигналинг и LiveKit RoomService, `web/src` — клиент, `deploy` — LiveKit и пример конфигурации Nginx. REST API: создание `POST /api/rooms`, состояние `GET /api/rooms/{id}`, запуск `POST .../start`, остановка `POST .../stop`, вход зрителя `POST .../join`, обновление сигнального билета `POST .../signal-ticket`, завершение `POST .../end`. `GET .../signal` — WebSocket управления и P2P-сигналинга. Запуск принимает `{ "hostSecret": "...", "transport": "p2p" | "server", "viewerLimit": "10" }`; остановка — `hostSecret` и текущую `generation`; первый вход зрителя — `{ "session": "" }`, повторный — выданную строку сессии.

Ссылки на протоколы: [LiveKit deployment](https://docs.livekit.io/transport/self-hosting/deployment/), [Screen Capture API](https://www.w3.org/TR/screen-capture/).

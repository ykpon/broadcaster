# Browser Broadcast — дизайн приложения

## Цель

Создать self-hosted веб-приложение, в котором ведущий без регистрации создаёт комнату, выбирает экран, окно приложения или вкладку браузера и передаёт изображение со звуком аудитории до 10 человек через медиасервер. Зрители подключаются по публичной ссылке и независимо регулируют громкость воспроизведения.

## Границы первой версии

- Одна активная трансляция на комнату.
- До 10 одновременных зрителей.
- Без аккаунтов, базы данных, чата, записи и истории трансляций.
- Комнаты эфемерные: существуют только во время трансляции и удаляются после ухода ведущего.
- Интерфейс на русском языке, адаптированный для компьютера и мобильного просмотра.
- Локальный запуск одной командой: `docker compose up --build`.

## Архитектура

Система состоит из трёх частей:

1. React/TypeScript SPA показывает стартовый экран, студию ведущего и плеер зрителя. Браузер получает медиапоток через `navigator.mediaDevices.getDisplayMedia()`.
2. Go API создаёт комнаты, выдаёт подписанные краткоживущие LiveKit-токены и предоставляет состояние комнаты. Собранный SPA раздаётся этим же сервисом.
3. Self-hosted LiveKit работает как SFU: ведущий отправляет один поток на сервер, а сервер раздаёт его зрителям. Медиа не отправляется ведущим каждому зрителю отдельно.

В Docker Compose входят Go-приложение, LiveKit и Caddy. Caddy служит единой входной точкой для HTTP(S) и WebSocket; LiveKit публикует диапазон UDP-портов для WebRTC. В режиме localhost приложение работает без домена. Для публичного развёртывания владелец задаёт домен и открывает указанные TCP/UDP-порты; Caddy выпускает TLS-сертификат.

## Модель доступа

При создании комнаты сервер генерирует:

- криптографически случайный публичный `roomId` для ссылки зрителя;
- отдельный случайный `hostSecret`, известный только ведущему;
- LiveKit room name, производный от `roomId` и не показываемый как credential.

Публичная ссылка имеет вид `/watch/{roomId}`. Ссылка ведущего имеет вид `/studio/{roomId}#key={hostSecret}`; секрет хранится во fragment URL, чтобы браузер не отправлял его как часть HTTP-запроса. Клиент передаёт секрет в теле запроса только при получении presenter-токена. Viewer-токен разрешает только подключение и подписку, presenter-токен — публикацию одного screen-share потока. Токены имеют короткий срок жизни.

Регистрация не требуется. Любой, у кого есть публичная ссылка, может смотреть трансляцию. Угадывание идентификатора комнаты практически исключено за счёт достаточной энтропии.

## Пользовательские сценарии

### Создание комнаты

На главной странице пользователь нажимает «Создать комнату». Go API создаёт эфемерную комнату и возвращает viewer URL и host URL. Интерфейс сразу открывает студию и предлагает скопировать публичную ссылку.

### Запуск трансляции

В студии ведущий независимо выбирает разрешение и частоту кадров:

- разрешение: `Авто`, `1280×720`, `1920×1080`, `2560×1440`, `3840×2160 (4K)`;
- частота кадров: `30 FPS` или `60 FPS`.

Приложение подбирает максимальный bitrate по комбинации разрешения и FPS: от 2.5 Mbps для 720p30 до 25 Mbps для 4K60. Конкретные значения собраны в одной конфигурационной таблице и могут быть скорректированы без изменения компонентов интерфейса.

После нажатия «Выбрать источник» браузер показывает системный диалог выбора экрана, окна приложения или вкладки. Если браузер поддерживает системный звук, ведущий может включить его в этом диалоге. Полученный поток публикуется в LiveKit как screen share. Переключение разрешения или FPS во время эфира меняет constraints трека и максимальный bitrate без пересоздания комнаты.

Выбранные значения являются запросом к браузеру, а не гарантией. Фактическое разрешение ограничено исходной поверхностью, частота — частотой обновления источника и возможностями браузера, а качество передачи — кодировщиком, компьютером и сетью. После начала захвата студия показывает фактические width, height и frame rate из настроек трека; если браузер снизил качество, рядом отображается понятное пояснение.

Полноэкранные приложения и игры поддерживаются в той мере, в какой браузер и операционная система предлагают их в системном диалоге. Ведущий может выбрать окно игры или весь монитор. Exclusive-fullscreen, защищённый контент и некоторые графические API могут давать чёрный или замерший кадр; приложение не обещает обход этих ограничений и рекомендует borderless-window/fullscreen-window либо захват всего монитора. Веб-приложение не выбирает процесс игры автоматически: стандарт Screen Capture требует явного выбора поверхности пользователем при каждом запуске захвата.

### Просмотр

Зритель открывает публичную ссылку. До начала эфира он видит спокойный экран ожидания. После публикации трека плеер подключает видео автоматически; если политика браузера блокирует звук, интерфейс показывает явную кнопку запуска воспроизведения. Зритель может менять громкость от 0 до 100%, отключать звук, переходить в полноэкранный режим и выбирать режим вписывания изображения.

### Завершение

Остановка системного screen-share или кнопка «Завершить эфир» снимает публикацию. Зрители видят завершённое состояние. Когда ведущий отключается, сервер запрещает новые presenter-сессии для прежнего экземпляра эфира и очищает комнату после короткого grace period.

## Интерфейс

Визуальный язык — тёмная broadcast-студия с графитовым фоном, ярким коралловым акцентом статуса LIVE и холодным синим акцентом действий. Не используются стандартные шаблонные hero-блоки и декоративные градиенты. Основной акцент — крупная область предпросмотра и ясная строка состояния соединения.

- Главная: название продукта, короткое объяснение, одна основная кнопка создания комнаты и карточка «как это работает» из трёх шагов.
- Студия: крупный preview, индикатор LIVE, таймер, число зрителей, отдельные selectors разрешения и FPS, фактические параметры потока, кнопки выбора источника/остановки, mute микшированного системного звука и блок публичной ссылки.
- Просмотр: видео почти на весь экран, лаконичная верхняя строка состояния и нижняя панель с громкостью, mute и fullscreen.
- Состояния ожидания, отказа в доступе, отсутствующей комнаты, переподключения и завершения оформляются внутри той же сцены без системных alert-окон.

## API и данные

- `POST /api/rooms` создаёт комнату и возвращает `roomId`, `viewerUrl`, `hostUrl`.
- `GET /api/rooms/{roomId}` возвращает безопасное публичное состояние: `waiting`, `live`, `ended`, а также число зрителей.
- `POST /api/rooms/{roomId}/host-token` принимает `hostSecret`, проверяет его constant-time сравнением и возвращает LiveKit URL и presenter-токен.
- `POST /api/rooms/{roomId}/viewer-token` возвращает LiveKit URL и viewer-токен, если комната существует.
- `POST /api/rooms/{roomId}/end` требует `hostSecret` и завершает эфир.

Активные комнаты хранятся в потокобезопасном in-memory repository. Перезапуск контейнера завершает все комнаты, что является ожидаемым поведением первой версии. Обработчики LiveKit webhook обновляют состояния и число участников; webhook проверяется подписанным секретом.

## Ошибки и устойчивость

- Входные данные и лимиты размера запроса проверяются на Go API.
- Ошибки не раскрывают секреты и внутренние детали конфигурации.
- На создание комнат и выдачу viewer-токенов действует простой rate limit по IP.
- Клиент различает отказ пользователя от screen capture, отсутствие поддержки браузером, потерю сети и завершение source track.
- Ошибка применения 4K или 60 FPS не завершает эфир: клиент сохраняет поток с максимально близкими доступными параметрами и показывает фактическое качество.
- LiveKit SDK выполняет переподключение; интерфейс показывает состояния `подключение`, `в эфире`, `переподключение`, `завершено`.
- При недоступном медиасервере пользователь получает понятное сообщение и возможность повторить подключение.
- Сервер ограничивает комнату одним publisher и десятью viewer identities; один браузер после переподключения сохраняет identity в `sessionStorage`.

## Конфигурация и эксплуатация

Репозиторий содержит `.env.example` с безопасными локальными значениями и пояснениями для `APP_URL`, `LIVEKIT_URL`, `LIVEKIT_API_KEY`, `LIVEKIT_API_SECRET` и домена Caddy. Production-секреты не включаются в образ и не коммитятся.

Docker images собираются multi-stage сборками. Health checks проверяют Go API и LiveKit. README описывает локальный запуск, публичное развёртывание, обязательный HTTPS для screen capture вне localhost и необходимые порты.

## Тестирование и критерии готовности

### Автоматические проверки

- Unit-тесты Go: создание/очистка комнат, проверка host secret, лимит зрителей, формирование grants токена, rate limit и переходы состояний.
- HTTP-тесты Go через `httptest`: успешные и ошибочные ответы API без внешнего LiveKit.
- Unit-тесты TypeScript: независимый выбор разрешения и FPS, таблица bitrate, fallback недоступных capture constraints, преобразование ошибок capture, viewer volume/mute и route parsing.
- Component-тесты: создание комнаты, студия до/после запуска, экран ожидания зрителя и блокировка autoplay.
- Production build клиента, `go test ./...`, `go vet ./...` и проверка `docker compose config`.

### Ручная проверка

Ведущий в Chrome/Edge создаёт комнату, копирует ссылку, выбирает экран/окно/вкладку, включает доступный системный звук и начинает эфир. Второй браузер открывает ссылку, получает поток через LiveKit, регулирует громкость и fullscreen. Отдельное изменение разрешения и FPS отражается на constraints и sender parameters; на совместимом 4K/60 Гц источнике проверяется режим 3840×2160 при 60 FPS, а на несовместимом — корректный fallback с отображением фактических параметров. Для игры проверяются borderless-window и захват всего монитора; exclusive-fullscreen документируется как best effort. Остановка системного шаринга переводит обоих участников в завершённое состояние.

Ограничения захвата основаны на стандарте [W3C Screen Capture](https://www.w3.org/TR/screen-capture/) и описании системного выбора источника в [Chrome Screen Sharing Controls](https://developer.chrome.com/docs/web-platform/screen-sharing-controls/).

Готовым считается приложение, которое запускается одной Docker Compose командой, обслуживает одну комнату с ведущим и десятью зрителями, не требует регистрации и выполняет все описанные сценарии с понятными состояниями ошибок.

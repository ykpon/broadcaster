# P2P и серверный транспорт — дизайн

## Цель

Добавить в существующее приложение второй способ доставки медиапотока: прямой WebRTC mesh между ведущим и зрителями. Перед каждым запуском или повторным запуском ведущий выбирает `P2P` либо `Через сервер` и задаёт лимит зрителей. Значение лимита по умолчанию — 10; продуктового верхнего ограничения нет.

Серверный режим продолжает использовать self-hosted LiveKit SFU. P2P-режим использует Go-бэкенд только для управления комнатой, сигналинга и STUN; аудио и видео через бэкенд не проходят. Если прямое соединение невозможно, приложение сообщает об ошибке и не переключается на LiveKit автоматически.

## Пользовательские требования

- Режим транспорта выбирается перед каждым запуском, включая запуск после паузы.
- Уже подключённые зрительские страницы автоматически переходят на транспорт нового запуска без перезагрузки и без новой ссылки.
- Лимит зрителей задаётся обычным числовым полем рядом с выбором транспорта и блокируется во время активного эфира.
- Поле принимает любое положительное целое. Верхнего продуктового предела нет; для сохранения точности клиент передаёт значение как десятичную строку, а сервер валидирует его как целое произвольной точности.
- Если введённый лимит меньше числа уже подключённых или временно зарезервированных зрительских сессий, новый запуск отклоняется. Существующие зрители не отключаются случайным образом.
- В интерфейсе P2P явно указано, что исходящий трафик и нагрузка ведущего растут с каждым зрителем, участники могут видеть сетевые адреса друг друга через ICE, а серверного fallback нет.
- В серверном режиме один исходящий поток ведущего по-прежнему поступает в LiveKit и раздаётся SFU.

## Архитектура

Система получает общий управляющий слой комнаты и два взаимозаменяемых медиатранспорта.

1. React/TypeScript SPA захватывает экран один раз через `getDisplayMedia`. Далее выбранный транспорт либо публикует треки в LiveKit, либо добавляет их в отдельный `RTCPeerConnection` каждого P2P-зрителя.
2. Go API хранит эфемерные комнаты, зрительские сессии, конфигурацию текущего запуска и его монотонный номер `generation`. Он выдаёт одноразовые билеты для управляющего WebSocket, маршрутизирует только разрешённые сигнальные сообщения и управляет жизненным циклом LiveKit-комнат.
3. Встроенная в тот же Go-процесс STUN-служба отвечает на стандартные UDP Binding Request. Она сообщает браузеру наблюдаемый адрес, но не ретранслирует пакеты и не является TURN.
4. LiveKit создаётся лениво только для запуска в режиме `server`. Недоступность LiveKit не мешает создать комнату или провести P2P-эфир.

P2P использует mesh-топологию: на каждого реально подключившегося зрителя ведущий создаёт один peer connection. Количество объектов и медиасендеров не резервируется по заявленному лимиту, поэтому даже очень большое значение поля само по себе не расходует память пропорционально этому значению.

## Модель комнаты и запуска

Новая комната создаётся со следующими значениями:

- состояние `waiting`;
- `generation = 0`;
- транспорт ещё не выбран;
- лимит зрителей `10`;
- пустой набор зрительских сессий;
- отсутствующая LiveKit-комната.

Каждый успешный запрос запуска:

1. проверяет секрет ведущего, транспорт и положительный целочисленный лимит;
2. отклоняет лимит меньше числа занятых мест;
3. вычисляет следующий generation и для `server` подготавливает новую LiveKit-комнату с именем, содержащим room ID и этот generation, ещё не меняя подтверждённое состояние комнаты;
4. повторно проверяет под блокировкой, что room generation и число занятых мест не изменились во время внешнего вызова LiveKit;
5. атомарно фиксирует новый `generation`, транспорт и нормализованную десятичную строку лимита;
6. завершает оставшиеся ресурсы прошлого запуска;
7. выдаёт ведущему одноразовый билет управляющего WebSocket и, для серверного режима, LiveKit connection data.

Если подготовка или повторная проверка не удалась, временная LiveKit-комната удаляется, а подтверждённые generation и конфигурация не меняются.

Уникальное имя LiveKit на generation не позволяет старому токену или задержавшемуся участнику попасть в новый запуск. При остановке текущая LiveKit-комната удаляется. При P2P-запуске ресурс LiveKit не создаётся.

Остановка захвата, кнопка паузы или закрытие студии переводит комнату в `waiting`, закрывает peer connections либо удаляет LiveKit-комнату и уведомляет зрительские управляющие соединения. Сама комната, ссылка и логические зрительские сессии остаются пригодны для следующего запуска. Явное действие «Закрыть комнату» сохраняет существующую семантику окончательного состояния `ended`.

Комната остаётся эфемерной. Существующая очистка пустой комнаты через час и удаление завершённой комнаты через десять минут сохраняются. Активное управляющее соединение ведущего или зрителя считается присутствием и сбрасывает время пустоты.

## Управляющий WebSocket и зрительские сессии

После нажатия «Смотреть эфир» зритель получает либо возобновляет серверную session identity, резервирует место и получает случайный одноразовый билет сроком 60 секунд. Билет передаётся первым сообщением уже открытого same-origin WebSocket, а не в URL; после успешной аутентификации он удаляется. Повторное подключение требует нового билета. Аналогичный билет ведущему выдаёт запрос запуска.

Управляющий WebSocket существует для обоих транспортов. Благодаря этому зритель остаётся логически подключённым во время ожидания, сразу получает смену generation и не зависит от трёхсекундного HTTP polling для переключения транспорта. HTTP status polling остаётся резервным механизмом отображения состояния, но не является транспортом сигналинга.

Бэкенд отправляет зрителю события:

- новый запуск: generation, transport, viewer limit и connection data для соответствующего режима;
- остановка текущего запуска;
- окончательное завершение комнаты;
- адресованное P2P SDP/ICE-сообщение.

В серверном режиме зритель по событию нового запуска подключается к LiveKit с выданным краткоживущим токеном. В P2P-режиме сервер уведомляет ведущего о готовом зрителе; ведущий создаёт offer, а answer и trickle ICE candidates проходят через WebSocket с обязательными room ID, generation и viewer identity, назначенными сервером.

Сигналинг не принимает произвольного адресата или identity от клиента. Бэкенд выводит их из аутентифицированного соединения, проверяет generation и разрешает только сообщения `offer`, `answer`, `ice-candidate`, `peer-ready`, `peer-failed`, `broadcast-ready` и `broadcast-stopped`. Сообщения прошлого запуска отбрасываются. Одно WebSocket-сообщение ограничено 256 КиБ, один peer — 256 ICE-кандидатами на generation, одно соединение — 512 сигнальными сообщениями в минуту. Эти защитные пределы относятся к сообщениям одного соединения, а не к пользовательскому лимиту зрителей.

Зрительское место освобождается при штатном выходе сразу, а при внезапном разрыве сохраняется на существующий 90-секундный период для переподключения. Ограничение сравнивается с количеством активных и зарезервированных session identity, а не с числом заранее созданных объектов.

## P2P-медиатранспорт

Ведущий создаёт один `RTCPeerConnection` на зрителя и добавляет текущие video/audio tracks через `addTransceiver`/`addTrack`. Для каждого sender применяются уже выбранные настройки качества: codec preference, maximum bitrate, maximum frame rate и degradation preference. Изменение поддерживаемых live-настроек применяется ко всем существующим sender; новый зритель сразу получает последние подтверждённые настройки.

Зритель принимает video/audio tracks, подключает их к существующим элементам проигрывателя и применяет выбранный playout buffer напрямую к `RTCRtpReceiver`, когда браузер предоставляет этот API. LiveKit fallback для настройки буфера применяется только в серверном режиме.

Ведущий является offerer. Renegotiation для обычного подключения не нужна: оба допустимых media transceiver создаются до offer, а отсутствие системного аудио отражается inactive/missing audio sender. При появлении нового зрителя создаётся независимый offer только для него.

ICE использует только встроенный STUN. TURN и автоматический fallback на SFU отсутствуют. После состояния `failed` либо 20 секунд без состояний `connected`/`completed` peer закрывается, зритель видит объяснение про NAT/firewall, а студия показывает число неуспешных прямых подключений. Ошибка одного зрителя не прерывает остальные peer connections.

Исходящая статистика P2P агрегируется по peer connections: суммарный фактический bitrate и packets отображаются суммой, а худшие доступные loss/RTT/quality limitation — как состояние эфира. В диагностике дополнительно показываются число установленных и неуспешных P2P-соединений. Серверный режим сохраняет текущую статистику одного соединения с SFU.

## Встроенный STUN

Go-процесс поднимает UDP listener одновременно с HTTP-сервером. Библиотека Pion STUN используется для разбора и формирования пакетов; собственная реализация бинарного формата протокола не пишется. Служба отвечает только на Binding Request корректным Binding Success с `XOR-MAPPED-ADDRESS`. TURN Allocate, credentials и relay не реализуются.

Конфигурация:

- `STUN_LISTEN_ADDR` — локальный адрес listener, по умолчанию `:3478`;
- `STUN_URL` — публичный ICE URL, по умолчанию `stun:localhost:3478` для локального запуска;
- в публичном развёртывании, например, `stun:stream.example.com:3478`.

Docker Compose публикует `3478/udp` из контейнера приложения. Для публичного развёртывания документация требует DNS на тот же хост и открытый/проброшенный UDP 3478. Это тот же бинарник и контейнер приложения, но STUN по своей природе использует отдельный UDP endpoint, а не HTTP URL.

Некорректный `STUN_URL` или невозможность занять UDP listener являются ошибкой запуска приложения. Shutdown context закрывает UDP listener вместе с HTTP-сервером. На один исходный IP действует token bucket 100 запросов в секунду с burst 200; ответ содержит только обязательные атрибуты Binding Success и остаётся сопоставимым по размеру с запросом, чтобы не создавать удобный amplification endpoint.

## Интерфейс студии и зрителя

В панели «Настройки эфира» перед запуском находится секция «Способ подключения» с двумя вариантами:

- `P2P — напрямую`: минимальный медиамаршрут, отдельная отправка каждому зрителю;
- `Через сервер`: один upload ведущего в LiveKit, SFU раздаёт поток зрителям.

Рядом находится поле «Лимит зрителей». Оно хранит строковый draft, чтобы не терять точность большого целого. Пустое, дробное, отрицательное значение или ноль получает inline-ошибку и не запускает эфир. Значение 10 используется по умолчанию. Атрибут `max` отсутствует.

Во время активного эфира транспорт и лимит недоступны для изменения. После паузы они снова активны; последнее подтверждённое значение остаётся в форме. Выбор можно сохранить локально как удобство, но серверным источником истины для каждого запуска является подтверждённая конфигурация комнаты.

Статус студии и зрителя показывает текущий транспорт. Для P2P рядом с выбором постоянно видны предупреждения об upload, IP/ICE и отсутствии fallback. Зритель при прямой ошибке получает отдельное действие «Повторить P2P-подключение»; оно создаёт новый peer connection в той же generation и не меняет транспорт комнаты.

Логическое состояние `joined` отделяется от состояния конкретного медиатранспорта. Поэтому ожидаемое закрытие LiveKit или P2P при паузе/смене режима возвращает плеер в «Ведущий готовится к эфиру», а не на кнопку первоначального входа.

## Изменения компонентов

### Go

- `internal/broadcast/server.go` хранит конфигурацию generation, произвольный viewer limit, сессии и ленивый lifecycle LiveKit вместо фиксированного лимита 10 и обязательного создания media room.
- Новый модуль управления соединениями инкапсулирует одноразовые билеты, WebSocket peers, адресованную маршрутизацию и broadcast событий комнаты.
- Новый STUN-модуль владеет UDP listener, rate limit и graceful shutdown.
- `cmd/server/main.go` валидирует STUN configuration, запускает оба listener и больше не делает доступность LiveKit условием старта всего приложения. LiveKit cleanup выполняется при старте best-effort и его ошибки отражаются только при выборе server transport.
- `compose.yaml`, `.env.example` и deployment docs получают UDP 3478 и публичный `STUN_URL`.

### Web

- Новый transport controller предоставляет одинаковые операции `start`, `stop`, `updateSettings`, `stats` и `dispose` для LiveKit publisher и P2P publisher.
- Отдельный P2P publisher управляет map `viewer identity -> RTCPeerConnection`, offer/ICE lifecycle и применением параметров ко всем sender.
- Viewer controller держит управляющий WebSocket, переключает LiveKit/P2P по generation и защищается от завершений старой generation.
- `Studio.tsx` и `Viewer.tsx` остаются владельцами состояния интерфейса, но сетевые state machines выносятся из компонентов и unit-тестируются без React DOM.
- `api.ts` получает типизированные room/start/join payloads; `RoomInfo` включает generation, transport и viewer limit.
- `styles.css` добавляет selector транспорта, числовое поле, предупреждение и адаптивное отображение без изменения общей визуальной системы.

## Безопасность и приватность

- Host secret остаётся только во fragment URL и передаётся в теле авторизованных POST-запросов.
- Одноразовые WebSocket-билеты случайны, короткоживущи, привязаны к role, room, generation/session и удаляются после использования.
- WebSocket принимает только same-origin подключения, имеет небольшой read limit и не поддерживает произвольные data messages между браузерами.
- Viewer не может публиковать через LiveKit, послать offer другому viewer или выдать себя за другую identity.
- P2P раскрывает peer network candidates участникам. Это неизбежное свойство прямого WebRTC и явно объясняется до запуска.
- STUN является публичным UDP-сервисом без пользовательской авторизации, поэтому принимает только необходимый минимум протокола и rate-limits источники.
- P2P не означает end-to-end identity verification: доступ по ссылке остаётся моделью доверия приложения. Шифрование media обеспечивается обязательным DTLS-SRTP WebRTC.

## Обработка ошибок

- Ошибка захвата происходит до регистрации нового запуска, пока клик пользователя сохраняет browser activation; захваченные tracks закрываются при любой последующей ошибке старта.
- Ошибка создания LiveKit-комнаты влияет только на `server`-запуск и не меняет последнюю подтверждённую generation.
- Невалидный лимит либо лимит ниже занятых мест отклоняется до остановки успешного текущего состояния.
- Разрыв управляющего WebSocket запускает до четырёх переподключений с новым билетом через 1, 2, 4 и 8 секунд. После четвёртой неудачи медиатранспорт закрывается и показывается явная ошибка.
- Все асинхронные callbacks содержат generation/session guard. Старые connect, offer, answer, ICE, stats и disconnect не могут изменить новый интерфейс или закрыть новый транспорт.
- Ошибка отдельного P2P peer изолирована. Остальные зрители продолжают смотреть.
- Если браузер не поддерживает необходимые WebRTC API, P2P-вариант остаётся видимым, но запуск сообщает о несовместимости; пользователь может после ошибки выбрать серверный режим вручную.

## Тестирование

Разработка идёт red-green-refactor.

Go unit/integration tests проверяют:

- создание комнаты без вызова LiveKit и default limit 10;
- принятие большого положительного десятичного viewer limit без продуктового максимума и отклонение пустого, нуля, знака минус и дроби;
- запрет запуска с лимитом ниже активных/зарезервированных сессий;
- увеличение generation только после успешной подготовки транспорта;
- ленивое создание и удаление уникальной LiveKit-комнаты для server generation;
- отсутствие вызовов LiveKit в P2P generation;
- выдачу, expiry, single-use и привязку WebSocket-билетов;
- изоляцию ролей, комнат и generations при маршрутизации signal messages;
- seat reservation, reconnect grace, stop/end и cleanup;
- настоящий UDP Binding Request к локальному STUN listener и корректный XOR-MAPPED-ADDRESS;
- отказ запуска при занятом STUN listener и закрытие listener по context cancellation.

Frontend unit tests проверяют:

- валидацию и сохранение строкового viewer limit без потери точности;
- выбор транспорта и блокировку конфигурации только на активном запуске;
- создание одного peer connection на готового зрителя;
- offer/answer/trickle ICE flow и фильтрацию stale generation;
- применение quality settings к каждому существующему и новому sender;
- закрытие всех peer connections при pause/switch/dispose;
- изоляцию peer failure и retry в той же generation;
- переход server → P2P → server без возврата логического viewer в начальное состояние;
- агрегацию P2P outgoing stats и сохранение текущей LiveKit-диагностики.

Playwright при работающем Compose проверяет два реальных браузерных контекста с тестовым canvas/audio capture:

- существующий LiveKit-сценарий;
- локальный P2P-сценарий через встроенный STUN/сигналинг;
- несколько P2P-зрителей и независимое закрытие одного peer;
- pause, смену транспорта и повторный запуск без reload зрительской страницы;
- применение изменённого лимита и отказ лишнему зрителю;
- понятную ошибку искусственно сорванного ICE без автоматического server fallback.

Финальная проверка включает `go test ./...`, `go vet ./...`, `pnpm test`, `pnpm run build` и `pnpm test:e2e`. Публичный NAT traversal дополнительно проверяется вручную на двух сетях, поскольку localhost-тест не воспроизводит symmetric NAT и firewall policies.

## Документация и развёртывание

README описывает оба транспорта, выбор перед повторным запуском, произвольный лимит, пропорциональный P2P upload и отсутствие fallback/TURN. Инструкция публичного развёртывания добавляет UDP 3478 и `STUN_URL`, оставляя текущие LiveKit TCP/UDP-порты только для server mode.

Текст не обещает, что STUN гарантирует соединение. Для сетей, где direct ICE невозможен, пользователь должен вручную выбрать «Через сервер». TURN остаётся возможным будущим расширением, но не входит в эту работу.

## Критерии готовности

- Ведущий перед каждым запуском выбирает P2P либо server и задаёт положительный целочисленный лимит с default 10 без продуктового maximum.
- Режим и лимит нельзя изменить во время активного эфира, но можно изменить после паузы.
- P2P media идёт напрямую между браузерами; Go обслуживает только signaling/STUN/control.
- Server mode продолжает работать через LiveKit и не регрессирует по качеству, аудио, диагностике и повторному запуску.
- Подключённый зритель автоматически следует за pause и сменой transport generation без reload или новой ссылки.
- P2P failure не переключает комнату на LiveKit и не прерывает успешные peer connections.
- Создание комнаты и P2P работают при недоступном LiveKit.
- Встроенный STUN доступен через опубликованный UDP 3478 и корректно завершается вместе с приложением.
- UI и README честно объясняют bandwidth, IP visibility и ограничения NAT traversal.
- Все автоматические проверки проходят.
